# SkillLoop Enhancement v3 — 产品方向冻结文档

**版本：** v3.0 Direction Freeze · 2026-11-17  
**状态：** 产品方向已由本轮讨论确认；技术细节由实施期审计决定，不代表代码已实现  
**目标基线：** `comp5241project/SkillLoop` 的 `feature/enhancement-v2` 分支  
**配套文档：** `SkillLoop_Enhancement_v3_Codex_Implementation_Plan.md`

## 0. 一句话定义

**SkillLoop v3 是一个以教师审核知识资料为基础、以可信案例为实践载体、以学生诊断结果驱动个性化学习的 AI 软件工程学习平台。**

教师提供网页链接或文档，AI 提炼知识笔记和学习目标，系统从**已有、可验证的案例库**推荐匹配案例。教师审核后将课程发布到公开课程库。学生选择课程，完成 Part 1 诊断，在 Part 2 获得依据**同一份教师课程资料**与个人诊断差异生成的学习解释及练习，再进入 Part 3 修复与 Part 4 验证。

**产品目标优先于迁就 v2 Course Studio 的旧形态。** 允许重新设计教师端 UI、数据层与新增服务；但不得擅自修改 Part 1–4 的任何代码。

## 1. 已冻结的产品决策

| ID | 决策 | 约束 |
|---|---|---|
| D01 | 入口分为 Demo、Public Course Library、My Learning、Teacher Studio | 未登录可体验 Demo 与浏览公开课程；正式学习需要学生登录 |
| D02 | 教师输入为一条公开可访问 HTTPS 链接，或 PDF、DOCX、TXT 文档 | 真正完成内容提取，不能只上传文件名、使用假内容或默认 mock |
| D03 | AI 从资料提炼结构化知识笔记、学习目标和来源依据 | 教师可编辑、审核、拒绝或重试；不得直接自动发布 |
| D04 | AI **只推荐现有可信案例库**内的案例 | v3 不生成新可执行案例、私有测试或修复 runner |
| D05 | 同一门课程绑定一个明确的案例版本和教学目标范围 | 课程版本与案例版本均稳定，不随意漂移 |
| D06 | 教师发布的知识笔记是 Part 2 个性化教学的可信内容基础 | 个性化教学必须受到教师笔记、实际诊断和规范案例事实约束 |
| D07 | 不同学生诊断到不同薄弱点时，Part 2 应有**实质不同的重点** | 差异包括目标、核心解释、案例证据、对应练习，而非同义改写 |
| D08 | 公开课程库默认展示每门课最新已发布版本 | 已开始学习的学生始终绑定原来的发布版本 |
| D09 | 允许完全重建 Teacher Studio 的外观与步骤 | 只复用有价值的底层能力，不为了适配旧表单牺牲需求 |
| D10 | **禁止修改 Part 1–4 代码，除非用户预先明确批准** | 无论改动多小、是否为“必要修复”，均不得自行实施 |
| D11 | 实现真正功能，不得以静态假数据冒充真实 AI 或真实发布流程 | 可用确定性测试夹具做 CI，但演示必须能验证真实生产路径 |
| D12 | Part 4 始终使用可信、已登记的验证机制 | AI/教师上传内容不得成为可执行测试或任意代码的来源 |
| D13 | 实施须遵守目标坚持与止损原则，出现触发条件立即暂停当前路径 | 不放弃目标，不重复无效试错，不扩大修改范围；超授权变更须申请批准 |

## 2. v2 基线事实与当前断点

已核对仓库代码与 `docs/enhancement-v2/M5-LEARNING-JOURNEY.md`：

1. 普通四阶段页面已经串联，普通 Part 2 (`knowledge-map/learning.js`) 能根据 Part 1 诊断请求实时 AI 生成课程并在浏览器本地缓存；**但它不读取教师发布的课**。
2. 教师已可在 `enhancement-v2/studio/course.html` 创建、编辑、审核和发布不可变课程版本，存储和权限基础存在。
3. 教师发布课程可由学生通过带 `?journey=1&course=…&version=…` 的路径进入四阶段，学习记录绑定学生及版本；该路径由 `shared/course-journey.js` 和 `enhancement-v2/m5-journey.cjs` 实现。
4. 正式 Journey 的 Part 2 目前使用教师讲解资料、确定性模板和预设练习；正式流程的实时 AI 生成尚未启用。被实际评分的核心练习仍由可信案例目标提供，而不直接取自教师发布的自由文本练习。
5. **当前正式 Journey 支持的案例选择器**（以 `enhancement-v2/m5-case-library.cjs` 为准）：`cart-checkout@1 / edge-cases` 和 `retry-queue@1 / edge-cases`，每个对应两类已支持的目标。其他 Demo 案例不能自动宣称具备完整正式 Journey。
6. 当前公开课主要通过单门发布课的 URL 访问；教师 `op=list` 接口返回教师草稿，不是公开课程目录。

因此 v3 的重点不是“多增加一个上传按钮”，而是将**教师可信知识 → 已支持案例 → 具体学生诊断 → 个性化 Part 2**建立可验证的数据关联。

## 3. 目标用户体验

### 3.1 未登录者

- 首页明确展示 **Try Demo** 与 **Browse Courses**，不强制登录即可浏览公开课标题、简介、相关案例和学习目标。
- Demo 继续使用现有普通四阶段原型及本地学习记录；界面上明确标为体验，不能混进正式个人学习进度。
- 点击已发布课程的 **Start Learning** 时，要求学生登录；教师身份进入 Teacher Studio。

### 3.2 教师：AI Course Builder

新教师端按自然任务组织，旧复杂表单不再定义默认 UI。

**Step 1 — Import source**
- 粘贴一条公开 HTTPS 链接，或上传 PDF / DOCX / TXT；展示标题、类型、处理结果及可信度提示。
- 提取失败、页面需登录、文档只有图片、正文为空等情况，显示真实错误与可重试/换来源的操作。

**Step 2 — Review knowledge**
- AI 输出课程标题建议、概要、2–5 个学习目标、按主题组织的知识笔记，并为关键事实提供来源片段/页码或 URL 定位。
- 教师可以直接编辑知识结构与文字；来源正文不应被任意学生访问；AI 没有权限替教师发布。
- 笔记与目标必须避免错误引用和与已验证案例事实冲突；教师最终负责审核。

**Step 3 — Match a case**
- 系统检索可信案例库，显示 1–3 个候选或明确的 No suitable case 状态。每个候选呈现对应知识点、要求/练习的对齐理由、能否完整支持四阶段及不匹配项。
- 不允许模糊地将任何代码片段都匹配为“完整可验证案例”。
- 教师明确选择案例并确认学习目标映射；不匹配时可更换材料或目标，**不伪造案例**。

**Step 4 — Preview & Publish**
- 教师看到学生将看到的课程介绍、审核过的知识笔记、选定案例和预计诊断/学习路径，确认后发布。
- 已有草稿保存、审阅、所有者权限和版本冻结能力可复用；具体实现允许重新设计。
- 不需要教师手动录入一串 `conceptId`、`requirementIds`、完整代码、rubric 等底层字段；高级调试细节可按需查看。

### 3.3 学生：Public Course Library 与 My Learning

- **Public Course Library：** 公开列出最新已发布课程，不显示教师草稿、私有点评或评分答案。
- **My Learning：** 登录后列出已开始的课程、固定版本、可继续学习的阶段以及简洁的活动状态；不把 attempted 直接称为 mastered。
- **Course overview：** 展示课程目标与知识笔记概览；完整资料可在学习期间随时查阅，但不强迫先读完整笔记再做诊断。
- **Part 1：** 复用已有可信诊断能力，输出学生的具体薄弱点/证据。
- **Part 2：** 同一份教师已发布知识笔记与案例版本作为事实来源，AI 根据该学生的 Part 1 诊断选择教学重点，生成针对性的解释与对应练习；保存到该学生的课程尝试中，刷新可恢复。不得把随机改写称作个性化。
- **Part 3/4：** 继续使用该案例已有的修复与可信验证能力，保留原本学习阶段及记录语义。

## 4. Part 2 的数据与教学边界

### 4.1 不变的输入

`CoursePublication(version)` + `TeacherApprovedNotes(version)` + `TrustedCase(caseId, caseVersion, conceptId, requirementIds)` + `AuthenticatedLearnerAttempt` + `VerifiedPart1Diagnosis`。

- 课程知识必须绑定已发布版本及内容摘要/哈希。
- 诊断必须来自**服务器内经认证的该学生该尝试记录**，不能信任浏览器自带的任意“我很弱”摘要。
- 可信案例事实来自服务器登记内容；AI 不能修改原要求、问题 ID、测试、预期结果或修复运行器。

### 4.2 AI 个性化的允许范围

可生成：本轮学习重点、概念讲解、与当前案例紧密关联的推理说明、根据学生诊断编写的练习、给学生答案的建设性反馈、建议回顾的教师笔记片段。

不可生成或暗示：隐藏测试、真实执行结果、官方正确修复已通过验证、教师未审核的“正式课程版本”、未经授权的其他学生数据。

输出结构必须可验证，且有明确来源：`objective / targetedRequirementRefs / diagnosticEvidenceRef / explanation / caseApplication / practicePrompt / sourceReferences / aiSource / promptVersion`。服务端须核查可引用需求 ID 和源内容引用；不能通过前端关键字切割长文来形成数据字段。

### 4.3 如何与现有固定练习和平稳衔接

**首选无侵入方案：** 新增 v3 的学生个性化学习页面/服务，在其中展示教师知识、AI 个性化讲解与补充练习；原正式 Journey 的**规范练习、阶段状态推进和可信验证**继续由既有 `api/courses?op=journey` 管理。个性化练习可以有明确标识的 AI 反馈，但不得冒充当前规范评分或自动改变 Part 3/4 的前置条件。

这意味着个性化补充练习与规范阶段检验会并存，直到完成后续经授权的整合。若“完全无缝的 Part1→新Part2→Part3 导航”无法在不修改既有 Part 1–4 代码或行为的情况下实现，**必须记录受限体验、提出精确变更申请，等待用户批准；不得通过暗中重定向、替换底层逻辑或伪造完成状态规避约束。**

### 4.4 可复现的个性化

- 同一学生、同一尝试、同一课程版本和同一诊断证据，应复用已经生成并存储的学习内容；刷新不得每次自动重抽课程。
- 诊断不同应导致教学重点和练习真正不同；不同学生的数据必须隔离。
- AI 失败时可显示已审核笔记/已有确定性教学（明确注明来源），并允许重试；**不能把回退内容标成 AI-generated**。
- 如学生回答被 AI 评价，必须保留原回答、重试与失败状态，不因网络错误丢失。

## 5. 案例匹配与演示

v3 第一版**仅从服务器认可的完整 Journey 案例库推荐**，无需支持上传任意代码并自动执行。

| 已验证案例 | 演示资料应覆盖的主题 | 能体现的诊断差异 |
|---|---|---|
| `cart-checkout@1 / edge-cases` | 购物车边界输入、空购物车求平均值、折扣区间检查 | 学生 A 重点理解 `empty-cart`，学生 B 重点理解 `discount` |
| `retry-queue@1 / edge-cases` | 指数退避上限、非法尝试次数 | 学生 A 重点理解 `backoff-cap`，学生 B 重点理解 `attempt-count` |

**演示主线建议：** 教师上传真实可提取的、涵盖 `empty-cart` 与 `discount` 的材料；AI 提炼并推荐 `cart-checkout`，教师确认发布；两个学生打开同一门课程同一个版本，在 Part 1 选择不同答案；Part 2 显示不同的教学重点、案例解释及练习；二者分别继续进入现有规范修复和验证。`retry-queue` 作为第二案例回归或备选演示。

演示文件与诊断答案可提前准备，但页面展示必须来自真实上传、AI 处理、教师发布及认证学生流程。CI 可使用确定性 mock 来测试结构；现场必须能区分 live AI、mock 与 fallback。

## 6. 技术与安全边界

1. **只读可信案例库。** 推荐器仅引用 `supportedCourses()` / `journeyCase()` 等服务器已登记案例及其公开要求；不读私有评价/隐藏测试作为 AI 生成上下文。
2. **资料导入安全。** URL 仅允许合法公开 HTTPS；对 DNS、所有跳转目标、私有/回环/元数据网络地址、协议、端口、内容类型、文件大小、请求时限做限制，防 SSRF。文件限制类型/大小、拒绝危险内容、清理临时文件；不执行上传脚本。
3. **解析可信度。** PDF/DOCX/TXT 提取正文；扫描件/图片型 PDF 无可用文字时明确失败，不偷偷把空资料当正文；不需要在 v3 首版加 OCR。
4. **防提示注入。** 上传正文与网页内容均视作不可信数据；不能覆盖系统指令、教师身份、隐私策略或模型允许输出的 schema。
5. **权属与公开投影。** 教师源文件及草稿默认仅教师本人可见。公开目录只给经授权发布的标题、简介、可见目标和案例元数据；学生仅可读取发布版的公开知识笔记及自己的尝试。
6. **版本不可变。** 课程发布后知识笔记、匹配案例、案例版本、内容哈希须被冻结；更新创建新版本，旧学生尝试永不静默升级。
7. **真实系统语义。** 练习提交不等于掌握，AI 反馈不等于可执行验证，AI 不可以替代 Part 4 已批准的测试。
8. **失败可恢复。** 上传、解析、生成、匹配、保存、发布各阶段均清楚呈现失败原因；教师已保存编辑和学生已提交答案不得被失败操作悄悄覆盖。

## 7. 明确禁止未经批准改动 Part 1–4 代码

用户给出的强制指令：**“不改 P1234 的代码，如果一定要先经过我同意。”**

**保护范围：**
- `learning-path/**`（Part 1）
- `knowledge-map/**`（Part 2）
- `interview/**`（Part 3）
- `correction-lab/**`（Part 4）
- 与上述阶段业务规则直接相关的 `shared/course-journey.js`、`shared/flow.js`、`enhancement-v2/m5-journey.cjs`、案例评估/验证及相应 API 契约。

保护的不只是文件位置，也包括实际行为：不可借修改共享路由或新代理层来暗中绕过已有阶段校验、替换记录或改变验收语义。

**允许在未获额外许可时做的事：** 审计与运行测试；创建 `enhancement-v3/**` 新页面、服务及新数据库迁移；新增向后兼容的课程目录、上传、知识生成、案例推荐、持久化、个人教学 API；在不改变现有 API 语义的前提下扩展非阶段性课程后台。共享导航和构建配置仅可作不改变阶段业务行为的非侵入式增量调整，并必须进行回归测试。

**审批门槛：** 如果发现任何需要修改保护文件/业务行为的需求，Codex 必须**停止该改动**，出具：涉及的精确文件与行/函数、为什么其他无侵入方案不足、拟改逻辑、数据契约影响、可逆性、测试计划及风险；明确向用户请求同意。**沉默或含糊回复不视为批准**。可以继续完成其他不依赖该改动的工作，但不得偷偷实施。

## 8. v3 验收标准（不可降级为静态演示）

- **V3-A01** 教师真实导入公开 HTTPS 内容和至少一种文件资料，能看到可核查的正文提取结果与出错提示；PDF、DOCX、TXT 均按冻结支持范围实现。
- **V3-A02** 真实 AI 依据上述材料生成结构化笔记、目标和引用依据，教师能够修改、保存、重新打开草稿。
- **V3-A03** 只推荐已支持完整 Journey 的可信案例；解释映射理由；无匹配时正确拒绝。
- **V3-A04** 教师完成真实 review/publish；发布版不可变，公开课程库自动出现，草稿不公开。
- **V3-A05** 未登录者可浏览公开课程，学生登录后可以开始、保存、恢复自己的课程版本和阶段。
- **V3-A06** 用同一发布版本及两条不同真实 Part 1 诊断记录，AI 生成**可核查的不同重点**的 Part 2 教学；讲解与练习有教师笔记及案例要求依据。刷新稳定恢复，不跨学生泄露。
- **V3-A07** 规范四阶段的状态和测试仍有效，不得把个性化 AI 补充练习当成 Part 3/4 的虚假完成证明。
- **V3-A08** 原 Demo、原教师已发布版、旧 Journey、原四个阶段的测试通过；禁止未经批准修改受保护代码。
- **V3-A09** 上传、AI 不可用、模型坏 JSON、错误匹配、版本冲突、认证过期与重放均有明确的安全失败处理。
- **V3-A10** 提供可复现的端到端演示操作和测试报告，区分 CI 模拟、实时 AI、可信 runner 和任何已知集成限制。

## 9. 不在 v3 第一版范围内

- 任意资料生成全新可执行软件案例、任意上传代码/测试并在服务器运行。
- 班级、选课审批、课程邀请、教师分配、收藏评分、复杂学习分析或推荐算法。
- 依赖扫描 OCR、会员/登录网页抓取、专用视频转写等不必要的导入能力。
- 在没有真实证据时给出 mastery 分数，或让 AI 改写既有可信测试结果。
- 以重新美化全部 Part 1–4 页面为前提的范围扩张。

## 10. 设计判断与尚待批准事项

- **已经冻结：** 用户体验、案例库匹配、教师资料为事实基础、Part 2 个人化、公开课程库、原 P1–4 代码保护。
- **由实现审计确定：** 新建 v3 数据表还是在不破坏旧读写的条件下扩展非阶段性课程表；AI 具体模型；抽取库；公开元数据字段；v3 课程 UI 的文件位置。

**成功不是“新 Course Studio 看起来简洁”，而是师生双方在真正运行的系统里，走通一套来源可信、案例受控、诊断驱动且可继续验证的课程体验。**

## 11. 目标坚持与止损原则（Codex 必须遵守）

**以正确、完整地实现需求为目标，不因困难轻易放弃，但不得盲目坚持错误的实现路径。**

1. **及时反思：** 当实现受阻或复杂度明显超出预期时，重新分析根因与技术方案。
2. **避免无效重复：** 不得在没有新证据或新思路的情况下，反复尝试相同或类似的失败方案。
3. **控制修改范围：** 优先采用最小合理变更，不为解决局部问题随意重构或扩大影响范围。
4. **主动调整方向：** 发现方案不合理时，主动寻找替代方案，不因已有投入而固执坚持。
5. **坚守工程底线：** 不得为了完成需求而牺牲正确性、安全性、稳定性或可维护性。

### 明确暂停条件

以下任一发生时，**停止当前实现路径**，先记录证据、重审方案，再决定继续、调整或回退：

- 同类问题连续尝试 **3 次**仍未解决。
- 修改范围或实现复杂度明显超出最初预期。
- 修复过程中持续引入新的问题或回归。
- 需要大规模重构、修改核心架构或突破现有约束。
- 无法确认问题根因，或缺乏证据证明当前方案有效。

暂停不等于放弃。Codex 应记录最早失败假设、尝试结果、根因证据、替代方案及其利弊；对仍在授权范围内且证据充分的新方案可继续执行，对高风险、超范围或者任何 **Part 1–4 代码**改动，必须先向用户提出明确审批请求，**收到明确同意前不得改动**。不得以新增代理、重定向或共享层替换等方式绕开这一约束。

**核心原则：坚持目标，不固执于方案；不怕麻烦，但不盲目折腾。**

v3 不因暂时无法接入完整学习流程就偷偷降低为静态展示。若受保护的 Part 1–4 导航/代码导致无缝衔接受阻，应完成其他可独立交付的功能，明确标注集成缺口，并提交受保护代码变更申请；**未经批准不得声称 V3-A06/V3-A07 所要求的完整集成已经达成。**
