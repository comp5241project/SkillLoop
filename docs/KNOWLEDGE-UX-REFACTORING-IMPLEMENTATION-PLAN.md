## 1. Executive Summary

Safeguard teacher and personal edits before reorganizing Knowledge into My Knowledge, Explore, Teacher Workspace, and Account & Data. Reuse the existing static pages, JavaScript, CSS, `/api/knowledge`, and Supabase schema. The five phases below are ordered so data safety precedes new navigation and interaction. The existing 13 API tests and `scripts/check_site.py` passed at the code baseline; they do not establish live Supabase behavior.

## 3. Target Information Architecture

`/knowledge-map/` remains My Knowledge. Add `/knowledge-map/explore.html` for the public directory and `/knowledge-map/account.html` for account and data controls. Keep `graph.html`, `concept.html`, `question.html`, `case.html`, and `teacher.html`, including `graph`, `topic`, `question`, `case`, `version`, and legacy `/knowledge-map/?topic=...` links. [`learning-path/script.js`](../learning-path/script.js) still generates the legacy link; `practiceHref` still points to Correction Lab. Teacher Workspace is shown as a role function while backend ownership remains authoritative.

Desktop graph pages use navigation, toolbar, canvas and context panel. Mobile pages stack the canvas and context panel. An empty personal graph offers Explore first, sample second, personal creation third. Static sample browsing does not depend on account service availability.

## 4. Target Component & State Architecture

- **Canvas:** draw nodes and typed edges, handle viewport, hit areas, focus and movement callbacks. Do not own API calls or mutate source graph data while rendering.
- **Data adapter:** public load and sample fallback; V1 local read; `knowledgeV2` read/write; account mapping. Keep `graphId:conceptId` and source snapshots stable.
- **Selection/view state:** one `{kind, id}` choice for node or relationship; separate query, highlights, focus, viewport and panel mode. Canvas and lists dispatch the same choice.
- **Personal workspace:** reference, note, personal node/edge and position commands; apply confirmed remote writes or restore a consistent draft on failure.
- **Public learning:** concept, relation, activities, question and case views use existing published payloads. A studied mark is self-reported; quiz feedback is local.
- **Teacher editor:** track clean, dirty, saving, saved revision, save error, review pending, reviewed, preview revision and published revision separately. A save captures a payload snapshot and editing sequence; an old response cannot mark newer edits clean. Publish only a saved revision.
- **Account/import:** report Local Mode, memory-only fallback, account identity, import preflight and transactional success/failure without clearing browser records.
- **Page states:** Loading, Empty, Error, Unauthorized, Unavailable and Save Failed each have a visible recovery action. Never render fabricated persistence success.

## 6. Phase 0–4 Implementation Plan

### Phase 0 — Baseline & Safety

**Files:** modify `teacher.js`, `personal.js`, `network-core.js`; add case-edit regression tests. Preserve model and historical SQL. **Responsibilities/UI:** case save retains hidden fields; personal note and drag failures restore a matching UI and in-memory value; teacher switches and leaves only after Save, Discard or Cancel. **API/data:** retain existing write shapes and draft revision checks. **Compatibility:** preserve multi-claim/link, path, archive and publication fields. **Tests/manual:** existing test baseline, multi-field round trip, network failure, 409, late response, switch/refresh. **Done:** no unrelated field loss or false Saved state and all baseline tests pass. **Rollback:** revert UI changes only; retain saved drafts, publications and personal data.

### Phase 1 — Navigation & Workspace

**Files:** modify `index.html`, `personal.js`, navigation/CSS; add Explore and Account pages plus minimal public-directory GET in `knowledge.mjs`. **Responsibilities/UI:** My Knowledge is contextual; Explore discovers published resources; account/import is separate; disabled backends show Local Mode. **API/data:** directory returns only public metadata; import remains explicit and transactional. **Compatibility:** old routes and sample fallback remain. **Tests/manual:** anonymous/student/teacher directory, no draft leakage, static mode, first reference, import preflight and failure. **Done:** new user can Explore → learn → reference → return. **Rollback:** hide the new directory route/entry if permission validation fails; leave old direct links and local data intact.

### Phase 2 — Graph Interaction

**Files:** modify canvas, personal/public pages, graph HTML/CSS; add narrowly scoped personal-edge reason update and additive SQL policy. **Responsibilities/UI:** edge or list selection opens relation details; search highlights canvas; personal create/edit uses explicit save/cancel/confirm. **API/data:** no personal `type` field is invented, no reference key or coordinates are rewritten. **Compatibility:** teacher relationships remain published read-only for students; current-version semantics remain. **Tests/manual:** mouse, keyboard list, dense graph, 300-node page, search/reset, failed writes and authorization. **Done:** AC03–AC05 pass in both personal and public graph contexts. **Rollback:** remove new selection/editor UI while retaining existing node and link reads; do not delete existing edges.

### Phase 3 — Learning & Teacher UX

**Files:** modify public learning pages, `teacher.html`, `teacher.js`, case helper and tests. **Responsibilities/UI:** show activities and existing practice links; distinguish materials, quiz and cross-module practice; teacher edits all claims/links and existing enum relation types, with visible preview/save/review/publish states. **API/data:** publish still names an exact saved revision; historical rows are immutable. **Compatibility:** keep `pathRole`, `order`, `icon`, `activities`, `practiceHref`, source metadata and archived records. **Tests/manual:** complete learner flow; multi-claim/link round trip; teacher save, preview, modify, rereview and publish with two roles. **Done:** AC06–AC08 pass without content loss. **Rollback:** retain already saved drafts and published rows; never reopen complex content through a lossy editor.

### Phase 4 — Regression & Polish

**Files:** expand tests/site checker; refine CSS and documentation. **Responsibilities/UI:** mobile and keyboard use, focus return, state feedback and recovery. **API/data:** no implicit migration or reset. **Compatibility:** V1, `knowledgeV2`, `knowledgeStudyV2`, seven IDs, historical URLs, teacher ownership, references and cross-module links. **Tests/manual:** automated suites plus static, mock and real preview environments recorded separately. **Done:** AC09–AC12 pass, no known data-loss path, and every real-backend gap is declared before release. **Rollback:** stop release and revert failing frontend/API version; preserve all user data.

## 7. API & Data Compatibility Assessment

The storage prefix remains `skillloop.v1.`. V1 `knowledge` is read as an initial local view and left intact. V2 nodes, edges and studied marks retain their keys and shape. Signed-in references retain source ID, version and snapshots. Personal teacher edges continue to reflect the current publication, while historical concept links use the reference source version. The UI must not label a current edge as a historical relation.

The public directory cannot use `my-graphs`, which is teacher-only and owner-filtered. It needs a separate anonymous read restricted to graphs with a current publication, using existing RLS and publishable-key access. Publisher names are omitted unless trustworthy public fields exist. A personal edge has no `type`; edit only its reason with authenticated, owner-scoped permission. Existing `GET public`, `POST import-personal`, draft and publication contracts remain stable. Import is one transaction, and client preflight is advisory rather than proof of success.

## 10. Dependencies & Open Blockers

**Recommended actual sequence:** Phase 0 losslessness → failed-write consistency → draft protection → Phase 1 navigation/empty state → public-directory permission verification → Phase 2 selection/context/search → personal relation editing → Phase 3 learning and teacher flow → Phase 4 regression. This order makes safety a prerequisite for richer editing.

**Must resolve before any release to another environment:** apply the additive personal-edge policy migration separately to each intended environment after review; verify public-directory RLS and grants there with an anonymous session. Teacher, learner, import and historical publication flows have been exercised on the configured non-production Preview as recorded below. Registration and import on a newly created account remain a useful additional QA scenario and need a confirmed disposable account or an accessible confirmation inbox; AC02 requires first use from an empty personal graph, which was verified on an existing account. The confirmed non-production project has already received and passed the migration; this does not authorize a production migration or deployment. Mock tests or a static server cannot replace environment-specific release checks.

**Can defer:** automatic graph layout, path sorting UI, fixed-version teacher edges, publisher-profile metadata, per-page review tracking and personalized recommendations.

**Phase 0 execution checklist:** record branch/SHA and existing worktree changes; run baseline tests; add multi-claim/link fixtures; fix lossy save; restore note/position UI on failure; guard draft switch/leave; capture payload and editing sequence on save; simulate 409, network failure and request reordering; rerun tests and record remaining live-environment gaps.
