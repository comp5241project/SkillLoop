# M2 AI teaching design — M2-01 preflight

**Status:** M2-04 isolated reliability and review gate implemented. No production UI, API, model call or shared contract change. Earlier stage descriptions below are retained as historical design notes.

## Verified identifiers and source boundaries

Current `cart-checkout` Case Definition v1 has `requirementId` values `quantity`, `ui-zero`, `discount`, `empty-cart`, `valid-totals`. These identify fixed requirement text; the legacy adapter pins exact source text before assigning IDs. `issueId` values are `negative-quantity`, `discount-range`, `empty-cart`. Relevant `testId` values include `discount-range`, `full-discount` and `empty-average`. Identical spelling of an issue and a test does **not** make their namespaces interchangeable.

| Proposed learning target | Requirement reference | Internal issue reference | Existing public test reference |
| --- | --- | --- | --- |
| A: empty cart | `requirementId: empty-cart` | `issueId: empty-cart` | `testId: empty-average` |
| B: discount boundary | `requirementId: discount` | `issueId: discount-range` | `testId: discount-range`, `full-discount` |

Only requirement IDs and approved requirement text belong in the generic student teaching context. Internal issue/test references in this table are for design verification, not generator input or default Student View output. Do not send `referenceCode`, `implementationNote`, Evaluation View, runner code, hidden assertions or teacher drafts to the model or learner.

## Input boundary for an isolated experiment

The isolated constructor accepts `{ fixture, factPack, previousObservationId?, previousAttemptId?, previousActivityId? }`. The **isolated preflight validator** checks case identity/version, authored answer IDs, requirement references and Module 1's actual `validateResult`. It is not a production teaching-input constructor. A future production boundary must validate AI-generated question sets where applicable and reject client-supplied summaries as independent evidence. Absent performance means `not_observed`; a supplied observation must pass the internal registry match or becomes `untrusted`. Public case facts and starter code come from the v1 Student View, not the private Evaluation View.

The two original fixtures and one reviewed wording variant in `enhancement-v2/m2-preflight/diagnosis-fixtures.json` are **synthetic deterministic student responses**, generated into complete local diagnosis records by Module 1's `buildLocalDiagnosis`. Their `edge-cases` evidence fields quote their actual response explanations verbatim. They are not real learner outcomes and are not AI output. All use the same case/version and authored four-question set. A and B share background (`student`) and goal (`build`); the wording variant initially shares A's profile. A's `code-reading` choice no longer asserts knowledge of the empty-cart result; B's `software-testing` choice no longer claims comprehensive boundary coverage. The options support the intended contrast, though semantic teaching quality still requires independent review.

## Output separation

At M2-01, the generator was deferred. The original proposed result separated these objects conceptually; M2-04 now enforces the supported student delivery path described below:

| `StudentLearningCardV1` — allowed for learner | `InternalAssessmentV1` — server/internal only |
| --- | --- |
| `caseId`, `caseVersion`, `conceptId`, `objective`, `requirementRefs[]`, `explanation`, bounded public starter-code excerpt, `exercise: {kind, prompt, publicHints[]}`, `origin: ai`, `promptVersion` | `targetGap`, diagnosis evidence provenance, expected answer features, rubric criteria, correct choice index if applicable, scoring guidance, safety/factual review notes, model metadata and validation errors |

No answer key, correct index, reference repair, internal rubric, private issue/test mapping or hidden test belongs in `StudentLearningCardV1`. The eventual API must project the student card by an explicit nested allowlist; internal assessment must never be spread into a response. The preflight does not create that API or claim deployment isolation.

## Adaptation and failure policy

- A's explicit answer shows uncertainty about `averagePrice([])`; target the `empty-cart` requirement with a trace and an exercise asking for the required numeric result and a check. The existing authored edge-cases card instead focuses on discount boundaries.
- B explicitly knows the empty-cart result but proposes testing only discounts 0 and 100; target the `discount` requirement with outside-range inputs and an exercise distinguishing accepted endpoints from rejected values.
- A response judged correct against the internal rubric advances to transfer practice; partial receives one narrower hint; incorrect returns to the exact requirement and a small code trace. This is a proposed decision rule, not implemented scoring.
- Invalid structure, unsupported reference, conflicting fact, prompt injection, timeout or model failure must fail visibly and preserve the student answer. Retry is bounded. Authored fallback requires an explicit choice and source label; it is never silently presented as AI output.

## M2-02 implemented data boundary

`enhancement-v2/m2-teaching-contract.cjs` implements five isolated functions: `buildFactPack`, `validateFactPack`, `buildTeachingContext`, `validateTeachingDraft`, and `projectPublicCard`. None is called by the existing four modules or a production API.

- **Fact pack:** The builder reads the M1 Student View from the trusted local legacy adapter, supports only `cart-checkout@1` / `edge-cases`, and copies case identity, title, scenario, `aiClaim`, exactly selected public requirement ID/text pairs and the original starter code. The validator rebuilds the canonical pack and rejects changed facts, unknown fields, unsupported concepts, wrong versions and issue/test IDs substituted for requirement IDs. It does not contain Evaluation View, reference solutions, runner internals or credentials.
- **Teaching context:** The builder checks the M2-01 preflight record, the actual Module 1 evidence quote and the selected priority. Module 1 supplies concept-level `level`, `evidence` and `gap`, but no trustworthy structured subtopic target. An internal human-reviewed mapping binds the complete diagnosis record, case/version and provenance marker to a specific `requirementId` using a pinned SHA-256 digest. The mapping includes A, B and a newly reviewed empty-cart record with different wording; `fixtureId` is not an authority key. A valid but unreviewed record gets `targetSelection: {state:'review-required'}`, and draft validation rejects it. A reviewed target is an experimental interpretation, not a semantic diagnosis guarantee.
- **Previous observation:** The default is `{state:'not_observed'}`. A simulated observation is accepted only if its internal registry entry matches the reviewed diagnosis's learner, attempt, case, version and concept, plus the requested attempt and activity IDs. Unknown IDs, missing provenance and mismatches return `{state:'untrusted'}` without any other learner's observed text. Caller-supplied IDs are selectors, not proof of ownership. Registry entries are private module data, not exported mutable objects. The complete-record digest prevents ordinary record changes from retaining the same review. A copied identical synthetic record can still impersonate its identity because this experiment has no production authentication; server-side authorization and genuine exercise assessment remain future work.
- **Proposed draft:** `publicCard` contains case/version/concept, objective, requirement references, explanation, an exact public starter-code excerpt and prompt, and a short-answer exercise with public hints. `internalAssessment` separately contains target gap, exact diagnosis quote, proposed expected elements, observable criteria, follow-up policy and mandatory `untrusted-proposal` status. `metadata` separately holds schema/prompt version, `ai-proposal` origin and a structural-review label. The validator enforces exact nested keys, bounds, identity, reference membership, exact starter-code excerpt provenance and reference-code exclusion. The public projector revalidates and explicitly rebuilds only `publicCard` fields; it never copies internal assessment or metadata.
- **Validation status:** A passing draft is *deterministically structurally validated and still needs human factual/teaching review*. The internal rubric remains an untrusted proposal. A rejected draft must not be displayed as a valid card. This layer does not prove that paraphrased teaching claims are true or that a production API keeps private data isolated.

## M2-03 isolated Mock generator

`enhancement-v2/m2-teaching-generator.cjs` exports `generateTeachingCard(input, provider, options)`. The provider interface is one injected `async generate(request)` method; no real AI SDK or network client is imported. The orchestration builds its own Fact Pack and original WeakMap-backed Teaching Context from the supplied diagnosis fixture. It rejects caller-supplied `context` or `targetSelection`, stops before provider invocation when the reviewed target is missing or a previous observation is untrusted, and retains the original context for `validateTeachingDraft` and `projectPublicCard`. A serialized reconstruction cannot retain that review authority.

The provider request is a separate JSON-safe allowlist: `schemaVersion`, fixed teaching task, public case identity/title/scenario/claim, selected public requirement text, public starter code, reviewed target requirement ID, quoted diagnosis evidence with question/option provenance, learner background/goal, and a validated-or-unobserved prior observation. It excludes review IDs, learner/attempt IDs, Evaluation View, reference code, private rubrics and runner internals. Student free text stays inside a data field and is not promoted to instructions. Requests and responses are bounded at 12,000 serialized characters.

The provider may return a structured object or JSON string. The generator invokes the existing M2-02 draft validator and public projection, then returns `success` with separate `publicCard`, `internalAssessment`, `generationMetadata` and internal `evaluationTrace`. Every success remains `human-review-required`; generated rubric status remains `untrusted-proposal`. Other outcomes are `review-required`, `invalid-input`, `invalid-output` or `provider-error`, with no public card. A failed generation may advertise an authored fallback option but never substitutes authored content automatically.

Retry policy: at most two provider calls, only for timeout, rate-limit or network-error codes. Malformed output, invalid input, permanent rejection and failed draft validation are not retried. Each provider call has a bounded timeout. Errors returned to the caller use safe categories without provider exception text.

Deterministic Mock A targets `requirementId: empty-cart` and proposes tracing `0/0` and `NaN`, with an empty-cart result exercise. Mock B targets `requirementId: discount` and distinguishes accepted `0`/`100` from rejected `-1`/`101`, with a boundary exercise. Both use the same public `cart-checkout@1` facts. The existing authored `edge-cases` card is discount-focused, so it is a relevant comparison for B and a limited baseline for A. Mock differences prove orchestration and fixture validity only; real AI personalization, factual quality, student learning outcomes and human quality review are **not tested**.

### M2-02R2 review authority at the draft boundary

The M2-02R independent review found that `validateTeachingDraft` trusted a mutable context's `targetSelection.state`. A caller could promote an unreviewed context and pass both draft validation and public projection. M2-02R2 associates only successfully reviewed contexts returned by `buildTeachingContext` with a module-private `WeakMap` entry containing a private copy of the validated fixture and a snapshot of the returned context. At each draft validation, the exact context object must have that private association, its current fields must match the snapshot, the public Fact Pack is revalidated, and the captured diagnosis is rechecked against preflight and the internal reviewed-evidence registry. Case, version, concept, review ID and requirement target must agree. `projectPublicCard` calls the same draft validator. The visible `targetSelection` is information for the generator, not proof of review; a clone, reconstruction, edited context or self-declared flag cannot create the private association. This process-local capability is not serialized or supplied by the caller.

The registry verifies only that a complete synthetic diagnosis matches one of three manually reviewed local records and, for the single simulated observation, that its reviewed record and requested attempt/activity/case identifiers match. The digest covers the complete diagnosis record, case/version and provenance, but an identical copied record has the same digest. It therefore does not establish a real user's identity or genuine exercise performance. A future service needs authenticated learner and attempt identity, server-side observation ownership and authorization. These remain separate from this isolated experiment.

## M2-04 isolated delivery and review gate

`generateTeachingCard` still returns an **internal draft result**. `JSON.stringify` of that result includes the proposed internal rubric, metadata and evidence trace and is unsafe as an API response. The supported `studentTeachingResponse(result)` function holds a process-local `WeakMap` registration for the exact result object and checks a private snapshot before every response. Pending or rejected states contain only a state, never a card. An approved response constructs a new card from explicit field allowlists at each nested level. Mutating the response does not alter the registered draft. Caller-supplied `approved`, `reviewed`, a clone, or a modified registered result cannot create or retain authority.

The lifecycle is `generated-pending-review` → `approved` or `rejected`; generator `success` means generation and deterministic checks succeeded, **not** publication. `reviewTeachingCard(result, reviewId)` cannot take an arbitrary approval decision. It looks up a module-private, immutable decision pinned to a SHA-256 fingerprint of the complete generated result and exact `caseId + caseVersion`. The registry contains `synthetic-a-acceptance-approval` and `synthetic-b-acceptance-rejection`, both with provenance `synthetic-acceptance-fixture`. They exercise both branches of the function boundary; **neither is an independent human teaching-quality evaluation or production decision**, and B's simulated rejection says nothing about B's teaching quality. Unknown IDs and nonmatching drafts remain pending. A production reviewer service needs authenticated decision capture, durable immutable draft identity, revocation, authorization and an API route that can serialize only the student response. This isolated projection does not prevent future code from incorrectly serializing the internal generator result.

`m2-factual-gate.cjs` runs after the M2-02 structural validator against the canonical public Fact Pack. The existing validator checks case/version/concept, requirement ID membership and exact public starter-code excerpt. M2-04 additionally rejects mismatched declared verbatim requirement quotes, the explicit contradictory claim “The empty-cart requirement is to return 999.”, named internal material markers in public prose and claims that tests were run or passed in this workflow. These rules are deliberately narrow. Different valid explanatory wording is allowed. The text “A shopper should get a negative total from an empty cart.” illustrates an unsupported semantic claim that passes deterministic checks but stays pending; a human must reject it. None of these checks proves arbitrary prose true, answerable, pedagogically useful or injection-safe for a real model.

The provider receives untrusted student evidence only as a data field inside the bounded request. Changes to a reviewed synthetic evidence record lose its pinned review and stop before provider invocation. Provider declarations of approval, unknown references, private markers and unexecuted-test claims fail output validation. This tests application decisions, not model resistance to prompt injection.

Provider calls accept an optional second argument `{signal}`. A timeout aborts the signal and waits up to 25 ms for settlement. If the provider settles after abort, one retry is allowed; if it ignores cancellation, the workflow returns `provider-error` without an overlapping retry. At most two attempts occur for `TIMEOUT`, `RATE_LIMITED` or `NETWORK_ERROR`; other errors and invalid drafts are permanent. Late results cannot change an already returned result or publish a card. Internal results expose only numeric `attempts` and `timeoutEvents` plus safe outcome codes; exception messages and student content are not logged by this module. AbortSignal cannot guarantee cancellation of an arbitrary provider's underlying work. Production telemetry must avoid request/response bodies and identifiers.

### Repeatable human review rubric

Review four items against the same `cart-checkout@1` public Fact Pack: Mock A (`empty-cart`), Mock B (`discount`), the reviewed paraphrase scenario, and the authored `knowledge-map/learning-content.js` `edge-cases` card. Preserve the exact draft, diagnosis record, requirement text, reviewer identity, date and evidence quotes outside student delivery. No independent human score is recorded yet.

| Dimension | Score 0 | Score 1 | Score 2 | Evidence to record |
| --- | --- | --- | --- | --- |
| Diagnosis relevance | Wrong gap | Mentions gap | Directly addresses evidenced gap | Diagnosis quote and targeted sentence |
| Objective alignment | Wrong requirement | Broadly related | Explicitly aligned | Requirement ID/text and objective |
| Factual correctness | Contradicts fact | Ambiguous | Accurate | Fact Pack quote and disputed claim |
| Explanation quality | Confusing | Partly clear | Clear causal explanation | Learner-facing passage |
| Exercise answerability | Unanswerable | Needs clarification | Answerable from public facts | Prompt and expected reasoning |
| Assessment consistency | Rubric conflicts | Partial match | Rubric matches prompt | Internal expected elements and prompt |
| Meaningful personalization | Wording only | Some target change | Objective, explanation and exercise change with gap | A/B side-by-side differences |
| Private disclosure | Private material present | Suspicious ambiguous hint | No private material | Exact field and source comparison |

Any factual contradiction, unanswerable exercise, or private disclosure is a **FAIL** regardless of total. Otherwise a candidate requires every dimension at least 1 and a total of at least 13/16 for human PASS. Two independent reviewers should record scores and resolve disagreements before publication. Automated checks establish schema and selected explicit facts only; the eight scores require human judgment. A/B differing text alone earns no personalization credit and demonstrates no learning improvement.

The authored `edge-cases` card explains discount range endpoints, uses a four-value choice exercise (`-1, 0, 100, 101`) and has a fixed correct index. It is a relevant strong baseline for Student B and may match or outperform Mock B. It does not directly teach Student A's empty-cart gap; the authored `code-reading` card does cover that fact and should be reported as an additional context check. The reviewed paraphrase is a diagnosis variant, not independently scored generated teaching. Record per-item scores and supporting quotes before any quality claim. A later real-model experiment must separately record latency, cost, retries, factual failures and learner outcomes; none are measured here.
